# Ajimu conventions

Work is finished only when it is verified, documented and committed cleanly.
These rules apply to every change; project-specific rules (CONTRIBUTING, local
agent instructions) take precedence where they are stricter.

## Finish-a-change checklist

Copy this checklist before committing and complete it in order:

```
Change checklist:
- [ ] 1. Run the project's real checks; note exact results (pass, fail, skipped)
- [ ] 2. Update the roadmap item: check it only if its exit checks really passed
- [ ] 3. Update CHANGELOG.md for any user-visible change
- [ ] 4. Update every document the change affects; keep "implemented" vs "planned" honest
- [ ] 5. Review the diff: intended files only, no secrets, no unrelated edits
- [ ] 6. Write a neutral imperative commit message and validate it
- [ ] 7. Commit with the owner's configured identity; never bypass hooks
```

If a check fails, fix it and run it again. Never mark a task done to move on.
Partial work is recorded as partial, with what remains.

## Comments: contracts, not syntax

Write source comments, identifiers and documentation in English. A comment must
add what the code cannot say:

- what a function promises: return values and their meaning;
- what it requires;
- what always holds;
- how it fails;
- **why** a non-obvious decision was made.

Do not narrate syntax: avoid comments like "increment the counter", which go stale
and add nothing. Every module starts with a one-line statement of its
responsibility. See [reference/comments.md](reference/comments.md) for examples.

## Documentation

- Update the roadmap, changelog and affected documents **in the same commit** as
  the code they describe.
- Keep a documentation index (`docs/README.md`) when a project has more than a few
  documents.
- Record each material decision as a short ADR in `docs/decisions/`, with context,
  decision, alternatives and consequences.
- Separate accepted decisions, assumptions, open questions and real blockers.
- Distinguish delivered behavior from plans. Never document an unexecuted check as
  passed.
- Prefer short, verifiable statements with exact commands and versions over prose.

Templates for the index, ADR, changelog and roadmap items are in
[reference/documentation.md](reference/documentation.md).

## Commit messages

- The subject is a concise English imperative, ideally 72 characters or fewer,
  describing the resulting behavior: `Preserve verified work across session
  restarts`.
- Add a body only when it explains the change, its reason, the checks or its
  limits.
- Subjects, bodies and trailers never mention AI, assistants, language-model
  tools, code-generation products or automated authorship, and **never** add
  `Co-Authored-By` or "generated by" trailers.

Check a message before committing with the script in this skill's folder:

```bash
python scripts/check_commit_message.py .git/COMMIT_EDITMSG
```

To enforce the check automatically, install it as a `commit-msg` hook: see the
script header. More examples are in
[reference/commits.md](reference/commits.md).

## Safety

- Use the owner's configured Git identity; never change global Git configuration.
- Respect `.gitignore` and local hooks.
- Never force-add ignored files, never use `--no-verify`, and never rewrite shared
  history.
- Keep account data, credentials, private notes and local tool configuration out
  of commits.
- A request to write or review a commit message does not authorize committing,
  pushing or publishing. Follow the owner's explicit authorization.
